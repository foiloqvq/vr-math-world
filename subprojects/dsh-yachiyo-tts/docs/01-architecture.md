# 架构与职责边界

## 为什么需要一个「桥接层」

DSH 朗读插件支持多种音色提供者，其中「本地 Index-TTS2」的契约是：

- `GET /health` → JSON（插件读 `model_loaded`）
- `GET /api/v1/voices` → `{"voices": ["..."]}`（字符串数组）
- `POST /api/v1/tts/tasks` → **返回 wav 字节**

而「月读八千代一键包」暴露的是另一套：

- `GET /health`
- `POST /tts?oneclick_token=<token>`，body 只需 `{"text","text_lang"}`，返回 wav 字节
- 只允许 `Host: localhost|127.0.0.1`；带 `Origin` 时必须在白名单内；`/tts` 必须有一次性 token

两边都能出 wav，但**字段名、鉴权、参数开放度完全不同**。与其改插件（会被插件更新覆盖），
不如在中间放一层翻译器——这就是 `bridge/server.py`。

## 三层职责

| 层 | 文件 | 职责 |
| --- | --- | --- |
| 桥接层（**本工程**） | `bridge/server.py` | 端点/字段翻译；**请求排队**；**退避重试**；长文本切段与拼接；**音频后处理**；把上游锁死的参数按配置注入 |
| 上游（第三方） | 一键包 `app/service.py` | 固定模型与参考音频；单飞锁；调用 GPT-SoVITS 推理 |
| 宿主侧（第三方） | 插件 `lib/index.mjs` / `lib/client.js` | 文本分块策略、播放调度、音色提供者选择 |

**原则：能用桥接层解决的，绝不去改第三方文件。** 本仓库的 `patches/` 只保留三处不得不改的地方，
且都附了理由与风险说明。

## 已实现能力

- 端点翻译：Index-TTS2 契约 ⇄ 一键包契约
- 长文保护：超过上游单次上限（3000 字）时按句切段、合成后拼接 WAV
- 可靠投递：内部串行（避免与上游单飞锁互踩）+ 429/5xx/连接错误退避重试
- 参数注入：切分方式、片段间隔、语速、采样温度、采样步数、超采样、参考音频
- 音频后处理：高通去闷、提响度、限幅（全部逐块固定参数，保证块间一致）
- 启动预热：等服务就绪后先合成两句，把 CUDA/模型预热掉，避免"第一次朗读等 30 秒"
- 可观测：`/status` 暴露当前生效的全部参数；`bridge.log` 记录每次合成的长度/耗时/大小
